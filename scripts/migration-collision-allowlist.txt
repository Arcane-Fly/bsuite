# Migration version-collision allowlist (bsuite#1707)
#
# All six submodules (crm7, conduit, R80.4, business-suite-unified, braden,
# throughput), the parent repo's own supabase/migrations/ ("root"), and
# packages/schema-builder/supabase/migrations/ ("schema-builder") deploy to
# the SAME shared Supabase project — this is the full 8-scope matrix in
# .github/workflows/supabase-migrate.yml. supabase_migrations.schema_migrations
# is one table keyed on the 14-digit version string alone, so any two files
# at the same version — in different scopes OR in the SAME scope — silently
# skip whichever one the applier reaches SECOND.
#
# Format: one entry per line,
#   `<14-digit version><ws>n=<count><ws><reason>`
# Blank lines and lines starting with # are ignored. Every entry below was
# verified by diffing the colliding files (see scripts/check-migration-
# version-collisions.mjs and the bsuite#1707 investigation notes).
#
# `n=<count>` is REQUIRED and is the number of colliding files the entry was
# verified against. It exists because this list is keyed on the VERSION alone,
# which meant an entry excusing one known-benign pair silently excused every
# FUTURE file at that version too. Proven by mutation on 2026-08-12: with
# 20260701090000 allowlisted for its crm7/business-suite-unified pair, planting
# an unrelated third migration in conduit at the same version still exited 0.
# That is the bsuite#1913 shape — a genuinely-losing migration merging because
# it happened to land on a timestamp somebody had already excused.
#
# So: if the group at an allowlisted version GROWS, the entry no longer
# describes it, and the check fails until a human re-verifies the whole group
# and updates the count. Adding an entry without `n=` also fails — stating the
# number you checked is the point.
#
# SHAPE (independent of the reason category below):
#   SAME-SCOPE  — all colliding files sit in ONE scope. Higher risk: one of
#                 them is DEFINITELY skipped by that scope's own migration
#                 loop the moment it records the first file's version,
#                 regardless of any other scope or job-ordering.
#   CROSS-SCOPE — colliding files sit in different scopes. Which one is
#                 skipped depends on which scope's matrix job the applier
#                 processes second — not a stable contract, but the loss is
#                 conditional rather than deterministic.
#
# REASON CATEGORY:
#   intentional-duplicate  — the SAME migration content, deliberately
#                             checked into more than one scope (byte-for-byte
#                             identical, OR identical DDL body with only a
#                             header-comment difference noting which copy is
#                             canonical). Applying it twice (or having one
#                             skipped) is a harmless no-op — there is nothing
#                             distinct to lose.
#   coincidental-timestamp — two GENUINELY DIFFERENT migrations that happen
#                             to share a timestamp by chance. Real risk: if
#                             the file that is skipped is the one carrying
#                             the collision, its DDL never runs in
#                             production. Historical (predate this gate).
#
# VERIFICATION STATUS (mandatory for every coincidental-timestamp entry —
# this script cannot query the live database; DB access is out of scope for
# the agent that built this gate):
#   CONFIRMED-DDL-LOSS   — checked against the live Supabase catalog. The
#                           DDL from (at least) one of the colliding files is
#                           confirmed ABSENT in production. A repair
#                           migration exists.
#   unverified — needs live-catalog check — not checked against the live
#                           database. Do NOT read as "confirmed harmless".
