## TL;DR

`@bsuite/theme@0.3.0` shipped to npm at **2026-04-22 09:36:25 UTC** with a nested CSS comment in `src/preset-v4.css` that broke the Tailwind v4 PostCSS parser (`Missing opening {`). It was detected three days later when consumer-app preview builds began failing on **2026-04-25 09:45 AEST** as the WS-D colour-token cleanup sprint started bumping consumers from `^0.2.0` → `^0.3.0`. The bug-fix release `0.3.1` (no semantic differences) was published **~25 hours later** at **2026-04-25 10:02:16 UTC**, and within the same session every consumer that had bumped to `0.3.0` was forwarded to `^0.3.1`.

**No production deploy ever shipped 0.3.0 to a public production alias.** Three consumer preview builds against 0.3.0 errored at build time (BSU, Conduit, Throughput — these never served bytes to a browser). Two consumer preview builds against 0.3.0 succeeded (CRM7, R80.3 — but neither imports the broken `preset-v4.css` entry-point, so even the served preview HTML/CSS was unaffected).

`@bsuite/theme@0.3.0` is now **deprecated on npm** (2026-04-27) with a deprecation notice pointing at 0.3.1. The version remains published (per CLAUDE.md doctrine — never unpublish, only deprecate) so any historical `pnpm install --frozen-lockfile` against an old lockfile still resolves; it just emits a deprecation warning at install time.

This doc closes the loop by formally narrating: what broke, when, who consumed it, and what changed in our publish process to prevent recurrence.

---

## 1. What Broke

`packages/theme/src/preset-v4.css` line 12 contained a nested CSS comment of the form:

```css
/*  ...prelude...  /* nested */ ... */
```

CSS comments do **not nest**. The Tailwind v4 PostCSS parser sees the inner `/*` as ordinary text and the `*/` as the comment terminator, then treats the trailing `... */` as malformed CSS, producing `Missing opening {` and aborting the build.

The fix in 0.3.1 was a one-character cosmetic change: rewrite the inner-comment marker as a `--` token, e.g. `/* ...prelude... -- nested -- ... */`. **No semantic colour-token, role-chain, or palette change** between 0.3.0 and 0.3.1.

## 4. Lockfile Poison-Pill Risk

**Risk: ZERO.** All 5 D2C consumer lockfiles on `development` and `main` resolve `@bsuite/theme` to `0.3.1`. There is no consumer with a stale `^0.3.0` specifier waiting for a `pnpm install` to silently re-pull the broken version.

CRM7's `origin/main` is currently on `^0.2.0` (the 2026-04-25 main release PR #308 was promoted before the 0.3.x sprint started). When the next CRM7 main promotion happens, it will bring `^0.3.1` directly — there is no path by which 0.3.0 could re-enter a main-tracked lockfile.

The `npm deprecate` (Section 5) provides an additional defence-in-depth: even if a developer manually pins `0.3.0`, `pnpm install` will print a deprecation warning citing this doc.

## 6. Lessons & Process Change

### 6.1 Root cause of the publish-process gap

`@bsuite/theme@0.3.0` was published with a build-script that produced the broken `preset-v4.css` byte-for-byte. The package's own internal tests passed (no consumer-style integration test ran the file through the Tailwind v4 PostCSS pipeline), the unit tests on the OKLCH role-chain calculations passed, and the publish workflow had no separate "consume-as-real-app" smoke test.

In short: `pnpm publish --access public` succeeded against bytes that `pnpm build` then `tailwindcss --postcss` (in a real consumer) would have rejected.

### 6.2 Concrete process change

Going forward, **every `@bsuite/*` package publish must include a consumer-style integration smoke** as the last pre-publish gate:

1. `pnpm pack` the candidate version into a tarball.
2. `pnpm install` the tarball into a throwaway minimal-Vite-+-Tailwind-v4 fixture under `packages/theme/test-fixtures/consumer-smoke/`.
3. Run `pnpm build` against the fixture.
4. Fail the publish if the fixture build errors.

This catches the entire class of "package builds fine in isolation but breaks the moment a real consumer's PostCSS pipeline parses it" bugs that the unit-test-only gate let through.

The consumer-smoke fixture lives in the same repo as the package, so it stays in lockstep with package source changes. The cost is ~30s added to each publish — acceptable given this incident.

### 6.3 Naming the anti-pattern

This pattern — **publish-then-validate-with-real-build** instead of **publish-after-validation-with-real-build** — is now formally banned for `@bsuite/*` packages. The fixture-smoke gate enforces it mechanically.
