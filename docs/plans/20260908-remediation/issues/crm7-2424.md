# control-boundary-contrast gate only reads inline className literals — computed classes are invisible to it

https://github.com/GaryOcean428/crm7/issues/2424

Snapshot updatedAt: 2026-09-04T13:24:24Z. Open at capture; re-read live.

## The gate checks less than its name suggests

`scripts/check-control-boundary-contrast.mjs` reads a control tag's own
**literal source text** — it finds `<input>`/`<select>`/`<textarea>`/
`<button>` (and a curated list of component wrappers), extracts that tag's
opening-tag text, and pattern-matches the class string written directly
inside it. It does not evaluate JSX, does not resolve `className`
expressions, and cannot see into a helper function's return value.

**This means the gate does not check controls. It checks controls whose
classes are written inline.** Any control whose `className` is computed —
via a `cn(someHelper(props), '...')` call, a `useMemo`, a variant map, or
any other indirection that isn't a literal string sitting in the tag's own
text — is invisible to it, regardless of what that computed string actually
contains.

Found via crm7#2423: `TrainingYearCalendar.tsx`'s `dayCellClasses()` returns
a bare `border-border` for its `'non-scheduled'` branch, consumed as
`className={cn(dayCellClasses(cell), '...')}` on a real `<button>`. The gate
scans that tag's literal text — `cn(dayCellClasses(cell), 'cursor-pointer
hover:border-border')` — sees no `border-border` substring in it (the actual
offending string lives inside `dayCellClasses`'s function body, dozens of
lines away), and reports nothing. The banked ratchet count (5) has held
through every fix landed against this gate today because none of those
fixes changed *what the gate can see* — only *how it classifies what it
already sees* (which variants are transient, whether a bracket value's
"active" names a pseudo-class, whether a downgrade on hover counts). This is
a different, deeper gap: a real violation that will never be counted no
matter how correct the variant logic becomes, because the scanner never
reads the line it lives on.

## Why this matters beyond the one file

Any page or component in either `crm7` or the shared `@bsuite/*` packages
that computes its control's className via a helper — a status-to-style
map, a `cva()` variant function, a `useMemo`-derived class string — sits in
this same blind spot. The true violation count is `>= 5` (the banked
ratchet), not `= 5`; the gap between them is currently unmeasured.

## What would close it

The gate would need to at minimum recognise the common `cn(helperCall(...),
'...')` / `cn(someVariable, '...')` shape and either (a) flag it as
`unknown` rather than silently passing when the tag's className expression
contains anything other than string literals, so the gap becomes visible
in the report rather than invisible to it, or (b) statically resolve simple
local helper functions (a small, closed set of cases — a `switch`/`if`
returning literal strings — rather than attempting general JSX/TS
evaluation). Option (a) is far cheaper and is the honest minimum: a check
that cannot prove a computed class is safe should say so, not stay silent.
