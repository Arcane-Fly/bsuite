# error_log has 618 rows whose message is literally [object Object], still occurring today — the one field that makes an error actionable is destroyed before the insert

Snapshot updatedAt: 2026-09-07T14:36:51Z. Open at capture; re-read live.

## `error_log` records 618 errors whose message is literally `[object Object]`, and it is still happening

Measured read-only against production on 2026-09-07.

```
error_log                    3,208 rows   (fatal 2,158 · error 1,050)
message = '[object Object]'    618 rows   first 2026-07-01 · newest 2026-09-07 13:00:31Z
last 7 days                     53 rows   of which 8 are '[object Object]'  (15.1%)
```

An error whose recorded message is `[object Object]` tells nobody anything. It is the log
equivalent of a gate that reports what it asked for instead of what it got: the row exists, the
severity is set, the timestamp is right, and the one field that would let someone act on it has
been destroyed by stringification before the insert.

`src/services/errorReporter.ts:183` inserts `report.message` straight into the table, and
`severity` defaults to `'error'` at `:107`. Somewhere upstream a non-Error value (an object, a
Supabase `PostgrestError`, a rejected promise's reason) is being coerced with template
interpolation or `String()` rather than having its `.message` / `.code` / `.details` read.

**619 of these would each have been a real, actionable error message.** Given what else is in
the same window, they are probably not duplicates of each other.

Two of those are worth their own attention: `Missing queryFn` ×8 is a react-query key registered

other direction.

## Two framings I am correcting, including one of my own

1. **Not-founds are not the problem.** It was suggested that cross-tenant deep links logging a
   legitimate not-found as `severity=error` makes this table unusable. Measured: rows whose
   message matches *not found* or *404* number **2 of 3,208 — 0.1%**, and both are the two an
   accountability probe wrote this afternoon. The concern is valid in principle and negligible in
   volume. It should not be the reason anyone touches this table.
2. **The biggest single entry is already fixed.** `useBranding must be used within a
   <BrandingProvider>` is 2,064 rows — 64% of the table — and would look like the headline. Its
   **last occurrence was 2026-08-13**, twenty-five days ago. It is historical. Counting it as a
   live problem would send someone chasing a bug that no longer fires.

That leaves `[object Object]` as the live one: 15% of the last week and current to today.

## Suggested fix

In `errorReporter`, normalise before recording: read `.message` from an `Error`, and for a
non-Error prefer `code`/`details`/`hint` (PostgrestError) or `JSON.stringify` with a depth guard,
falling back to the constructor name rather than `[object Object]`. Then a one-line guard: refuse
to insert a message that is exactly `[object Object]` — record the serialised shape instead. That
guard would have surfaced this on the first occurrence in July rather than after 618.

Measurements read-only; no writes, no DDL. I did not delete any rows.
