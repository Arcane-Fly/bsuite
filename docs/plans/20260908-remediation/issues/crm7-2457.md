# Numeric inputs that treat a valid zero as absent: 12 sites, two halves, one fixed

https://github.com/GaryOcean428/crm7/issues/2457

Snapshot updatedAt: 2026-09-05T14:22:43Z. Open at capture; re-read live.

Umbrella for the class that #2449 turned out to be one member of. Established by the enforcer gating #2452, which swept three axes rather than one and found twelve defective sites where my own token sweep had found a single one.

## The class, stated as a symptom

**A numeric input that treats a valid zero as absent.** That sentence is the class, and it has two halves that share no vocabulary, which is why searching for a spelling misses most of it.

**The payload half.** `onChange(e.target.valueAsNumber || null)`. A typed `0` is falsy, so it is stored as null. This is #2449 and it is fixed by #2452.

**The display half.** `value={x || ''}`. A *stored* zero renders as a blank field. Same symptom for the user, and it contains no `valueAsNumber` at all.

A third shape belongs to the class and matches neither search, because its fallback is not zero: `parseFloat(raw) || 1` on a penalty multiplier silently substitutes a different number rather than clearing the field. That one is money and is filed separately as R80.4 #313.

## Count

Twelve defective across the axes swept: the token, the idiom with a mismatched fallback, and the display side across all 137 `type="number"` inputs in 70 files in six apps. #2452 fixes one of the twelve.

Five were re-opened and confirmed by hand, including a leave balance on a person's record with `min={0}`, and both the hours and the rate on an invoice line. Those are pages users reach every day.

## The pattern to copy, which already exists here three times

The correct discriminator is the raw string, not falsiness, because HTML value-sanitization forces the value to an empty string for anything unparseable — so "no parseable value" and "NaN" are the same set, and zero is neither.

`SchemaDrivenFilterForm.tsx:213`, `DynamicFieldRenderer.tsx:131` and `award-rates/create.tsx:758` each do it correctly already: check the raw string, and use `??` rather than `||` on the display side. React Hook Form's own `getFieldValueAs` discriminates the same way, which is why the two compliance pages registering with `valueAsNumber: true` are not affected.

## Priority note

Fix the reachable ones first. `fetchCustomPage` filters on `is_published`, and production holds two custom pages, neither published and neither containing a field, so the surface #2452 repairs is one no user currently reaches. The eleven remaining sit on pages they do.

## Acceptance

Per site: typing `0` stores `0` and displays `0`; blank and unparseable input still yield the intended absent value; and where the fallback is a non-zero number, that substitution is either removed or made visible. Tests must fail against the current expression at each site — a test using only positive values passes everywhere today.
