# /people's row bound is createEntityStore's .range(), and nothing guards it

https://github.com/GaryOcean428/crm7/issues/2509

Snapshot updatedAt: 2026-09-06T16:18:35Z. Open at capture; re-read live.

`src/components/common/DataTable/__tests__/row-render-bound.test.tsx` (added in #2507) guards that `EnhancedDataTable` renders one page rather than every row. **It does not cover `/people`, and `/people` is the one route that needs a different guard.**

## The gap

`src/pages/people/index.tsx:616` sets `manualPagination`. On that path TanStack Table v9 **deliberately** returns the *pre*-paginated row model — `table_getPaginatedRowModel` returns `getPrePaginatedRowModel()` when `manualPagination` is true. The component hands every row it was given straight to the DOM, by design.

So `/people`'s bound is not the component's. It is `createEntityStore`'s `.range(from, to)` — `src/stores/peopleStore.ts:15`, `defaultPageSize: 25`.

**Delete that `.range()` and `/people` renders everything it fetched, while `row-render-bound.test.tsx` stays green.** Right outcome today, different mechanism, no guard on the path that actually holds it.

This is the "a defect in the harness cannot be guarded by a behavioural case" shape: the existing test asserts the wrong mechanism for this route, and would report green through the regression.

## Scope

`manualPagination` is set at exactly one call site today (`grep -rn "manualPagination" src/pages/ --include=*.tsx`, excluding tests → 1 result). The guard should be at the **store**, not the page, so a second server-paginated route inherits it.

## Acceptance criteria

- A test asserts that `createEntityStore`'s list query applies a bounded `.range()`, and **fails** when the range is removed — demonstrated in the PR, both directions.
- It is written so a store added later is covered without editing the test, or the test names why it cannot be.
- `row-render-bound.test.tsx`'s header stops being the only place this gap is recorded.
