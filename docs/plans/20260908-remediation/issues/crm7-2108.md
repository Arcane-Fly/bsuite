# Back-navigation affordances: 4 wording variants + icon/variant drift across ~220 call sites

https://github.com/GaryOcean428/crm7/issues/2108

Snapshot updatedAt: 2026-08-27T02:05:10Z. Open at capture; re-read live.

## Context

Follow-up from crm7#2061 (note.110, "Back to X nav links styled inconsistently"). PR (this repo, branch `fix/issue-2061-back-to-x-consistency`) fixed the one genuinely bare/unstyled instance and introduced a shared `BackButton` component (`src/components/common/BackButton/`), but a full re-derivation of the sibling count turned up a much larger and differently-shaped class than either the issue or the prior PR (#2100) estimated. This issue tracks the remainder honestly rather than letting it look silently closed.

## What re-deriving the count actually found

Not "some plain text, some buttons" as hypothesized. Measured by reading each call site's surrounding JSX (not just grepping the string), virtually every back-navigation affordance in this codebase is **already** a real `<Button>` (or routed through `EmptyState`'s button-rendering `action`/`primaryAction` prop). The real defect is **wording and styling drift across four independent phrasings of the same control**, plus one genuinely bare link:

| Wording variant | Search | Real matches | Already a real `<Button>`? |
| --- | --- | --- | --- |
| `"Back to X"` | `grep -rn "Back to "` | 106 (1 prose false-positive excluded) | 105/106 — 1 bare `<Link>` (fixed this PR: `src/pages/portal/host-reports.tsx`) |
| `aria-label="Go back"` (icon-only) | `grep -rn '"Go back"'` | 75 raw, 73 real (2 are onboarding-wizard prev-step controls, a different affordance) | 73/73 — but 1 used `variant="outline"` instead of the other 72's `ghost` (fixed this PR: `vet/qualifications/[id]/structure.tsx`); icon size also split 58×`h-4 w-4` vs 14×`h-5 w-5` (not fixed) |
| `"Return to X"` | `grep -rn '"Return to '` | 9 | 9/9 |
| bare `"Back"` (no "to X") | `grep -rn '>Back<'` (sampled) | ~30 | not individually re-verified per-site; sampled entries are `<Button>`-wrapped |
| literal `"← Back"` (arrow character, not an icon component) | `grep -rn '"← Back"'` | 3 | 3/3 — all `<Button>`, but using a text glyph instead of the `ArrowLeft` icon used everywhere else |

**Icon choice also varies for the identical action**: `ArrowLeft` (majority), `ChevronLeft` (at least `src/pages/hosts/[id].tsx` and others — verify `ChevronLeft` isn't also legitimately used for calendar prev/period controls before treating a hit as this class), and the literal `←` character above.

**Running total measured: ~218-220 real back-navigation call sites across at least 4 wordings and 2 icons.** This is almost certainly not the full population — the bare-`"Back"` sample was not individually verified, and there may be more wordings/icons not yet searched for. State a fresh denominator before touching this; do not assume the count above is final.

## What this PR fixed (see the PR for evidence)

- The 1 confirmed bare/unstyled instance (`portal/host-reports.tsx`).
- The 1 confirmed variant-outlier in the "Go back" icon-only class (`vet/qualifications/[id]/structure.tsx`).
- Consolidated 6 byte-identical "Back to WHS" duplicates onto the new shared `BackButton` component.
- Introduced `src/components/common/BackButton/` as the canonical shared affordance (supports both the labeled and `iconOnly` shapes).

## What's left (this issue)

1. **Unify wording.** Pick one of "Back to X" / "Go back" / "Return to X" / bare "Back" as the standard (recommend "Back to X" for the labeled case — most discoverable per crm7#2061's own framing — and reserve icon-only for tight header rows) and migrate the remainder onto `BackButton`.
2. **Unify icon.** Standardize on `ArrowLeft` (already the majority); replace `ChevronLeft` and literal `←` usages.
3. **Unify icon size** in the icon-only class (16px vs 20px split, 58 vs 14).
4. Re-verify the bare-`"Back"` sample (~30 sites) individually — it was sampled, not exhaustively confirmed, in the sweep that produced this issue.
5. Consider a lint rule (`bsuite/no-hand-rolled-back-button` or similar) that flags a `<Button>` wrapping an `ArrowLeft`/`ChevronLeft` + navigate/Link combination outside of `BackButton` itself, so the class can't silently regrow.

## Separate, more important finding: the round trip is lossy regardless of styling

Live-verified against production (`crm.crm7.app`, signed in as `e2e@crm7.app`): list pages (`/leads` confirmed; `/hosts`, `/mentors` read the same way in source) keep filter/search/sort/pagination state in plain component `useState`, not the URL and not a persisted store. Typing a filter on `/leads`, opening a lead, and clicking its "Go back" button returns to a bare `/leads` with the filter silently cleared — confirmed live (`filterSurvived: false`). This is independent of whether the back control is styled as a button or a plain link; it happens because the list component unmounts and remounts with default state. Fixing it needs the list pages to read/write filter state via the URL (or a persisted store) and rehydrate on mount — a larger, cross-cutting change out of scope for a "make the back buttons consistent" PR, but worth its own ticket since it costs users real work (re-entering filters) every time they use the very affordance this issue is about.
