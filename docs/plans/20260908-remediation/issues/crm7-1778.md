## Why this is not a lane disobeying an instruction

Migration `crm7/supabase/migrations/20260806165000_unfreeze_placement_rate_provenance.sql` applied on **6 August**, seven days before the 13 August directive was written. Its `UPDATE` predicate is:

```sql
where charge_rate is not null
  and (award_rate_resolution_status is null
       or award_rate_resolution_status = 'unresolved')
```

It swept `unresolved` and `NULL` together, because at the time both were simply "rows frozen by a NOT VALID CHECK that Postgres re-checks on every update". The distinction the operator later drew — that `unresolved` *means resolution ran and failed*, and `NULL` means it never ran — had not been stated when the migration was authored.

**No dollar figure was changed.** `manual` asserts provenance only: a human set this rate rather than it being resolved from an award. Every one of the twelve has `award_rate_id IS NULL`, so none was ever award-resolved.

## What was actually lost

The ability to tell, in the operator's own demo tenant, which placements had a **failed resolution attempt** versus which were simply typed in. That is a diagnostic signal about the resolver, not about the money.

## The decision — three options

**Option A — accept the loss, record it, move on.** *Recommended.*
Restoring `unresolved` re-creates the exact P0 the migration cured: the constraint is now `VALIDATE`d, so writing `unresolved` back onto a row that has a `charge_rate` would be **rejected outright** by Postgres. To restore the label the charge rates would have to be nulled first, which loses real data to recover a diagnostic. The twelve rows are in `bsuite Platform`, a demo tenant with no client exposure. Cost: one line in the directive's status record.

**Option B — restore the signal without re-freezing.** Add a nullable `award_rate_resolution_last_error` (or a row in the existing charge-rate audit log) recording that these twelve had a failed resolution before 2026-08-06, then re-run the resolver against them and let it write a truthful current result. Cost: one small migration plus a resolver run. Keeps the constraint intact. Choose this if the *resolver failure* is the thing worth knowing, rather than the label.

**Option C — restore `unresolved` literally.** Requires nulling `charge_rate` on twelve rows or dropping the constraint. **Not recommended** — the ruling itself says do not drop the constraint, and nulling the rates destroys more than it recovers.

## Not a defect, checked and disproved

The migration header warned: *"The code fix accompanies this migration; without it, an edit that clears award_rate_id would re-freeze the row."* A grep for `award_rate_resolution_status` in `src/pages/placements/[id]/edit.tsx` returns **zero**, which reads like the code half never landed. It did — the rule lives in the shared helper `withRateProvenance(...)`, called at `edit.tsx:340`, with the reasoning in a comment above it. **The zero was an artefact of grepping for a literal that a helper hides.** No action needed on the write path.

## Reproduction

```sql
-- 1. no unresolved rows survive
select count(*) from placements where award_rate_resolution_status = 'unresolved';   -- 0

-- 2. the twelve, one transaction
select id, charge_rate, award_rate_id, updated_at
from placements p join tenants t on t.id = p.tenant_id
where t.name = 'bsuite Platform' and p.award_rate_resolution_status = 'manual'
order by updated_at;      -- 12 rows, all 2026-08-06 07:03:46.244379+00

-- 3. the constraint is real now, not merely blocking
select conname, convalidated, pg_get_constraintdef(oid)
from pg_constraint where conname = 'placements_resolved_rate_required_chk';
```

**Filing is not fixing.** This issue changes nothing; it puts a decision in front of the operator that would otherwise be lost in a directive nobody re-reads.
