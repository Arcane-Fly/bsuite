# [P1] Five portal routes have no permission gate, and PortalScopeGate fails open by design

https://github.com/GaryOcean428/crm7/issues/2502

Snapshot updatedAt: 2026-09-06T11:20:54Z. Open at capture; re-read live.

## What

Five portal routes are registered with **no `permission` prop**, and the scope gate that was
meant to cover them **fails open by design**. The database is currently the only real
boundary on these pages.

## Measured

**1. No route-level permission.** In `src/App.tsx`:

```jsx
<ProtectedRoute path="/portal/training-provider" ... routeName="Training Provider Portal" />
<ProtectedRoute path="/portal/host-employer"    ... routeName="Host Employer Portal" />
<ProtectedRoute path="/host/reports"            ... routeName="Host Monthly Reports" />
<ProtectedRoute path="/portal/worker"           ... routeName="Worker Portal" />
<ProtectedRoute path="/portal/workplace-portal" ... />
```

No `permission=` on any of them. Other routes in the same file do gate —
`permission="manage_contacts"` and similar appear throughout. So `ProtectedRoute` here means
**authenticated**, nothing more: any signed-in user reaches these by typing the URL.

**2. `PortalScopeGate` fails open, and its own docstring says so.**
`src/lib/portal-scopes.ts`:

> "Until that hook is registered by the operator, the JWT will **NOT** carry a `scopes` claim
> — all `hasPortalScope` calls will return `false` in that case. The portal pages render a
> graceful **'scope pending' notice** rather than an error."

`parseScopeClaim` returns `[]` when the claim is absent, "so all `hasPortalScope` calls
degrade gracefully". The `inject_portal_scope_claims` Custom Access Token Hook was never
registered, and the OAuth-scopes work was rolled back.

So the absence of a scope claim — which means **"we could not tell"** — renders a notice
instead of denying. That is the same habit as reading a NULL that means *unknown* as though
it meant *unrestricted*, and it has produced several defects on this estate already.

## Severity, stated accurately

This is a **missing layer, not a demonstrated leak**. What a user actually sees is still
constrained by RLS, so the exposure is that route gating contributes nothing and everything
rests on the database being right.

That is exactly the situation crm7#2496 was written to address — and it is why that PR
matters more than its own description suggests. Until #2496 lands, a `host_supervisor`
reaching `/portal/host-employer` reads rival hosts' `employers`, `clients`,
`training_contracts`, `invoices` and `invoice_line_items`, and **nothing above the database
would have stopped them**.

It also makes **#2498** — "the route gate checks a permission, not whose host it is" —
considerably more urgent than the copy issue it is currently filed as. There is no route
gate on these pages at all.

## What this needs

1. **Give each portal route a `permission`**, matching the audience it names. A route called
   "Host Employer Portal" should not be reachable by a worker, a training provider, or an
   unrelated staff member.
2. **Decide `PortalScopeGate`'s disposition explicitly.** Either register the token hook and
   make the gate real, or remove it — a gate that renders "scope pending" for every user
   forever is worse than no gate, because its presence reads as coverage.
3. **When it is real, it must fail CLOSED.** An absent scope claim denies; it does not
   explain.
4. **Add a test that a user of the wrong role cannot reach each portal route** — the class
   here is "authenticated is not authorised", and it needs a positive control (the right
   role reaching it) so the test cannot pass by denying everyone.

## Acceptance

- Each portal route names the permission it requires.
- A wrong-role user gets denied, proven by test, with a right-role control passing.
- `PortalScopeGate` either enforces or is gone, and if it enforces, an absent claim denies.
- The route-level and RLS-level boundaries are **independent**, so neither is the only one.

Found while gating crm7#2496. Related: #2498, #2500, #1675.
