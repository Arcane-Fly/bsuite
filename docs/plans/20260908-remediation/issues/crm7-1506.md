# 17 migrations fail on CI replay — every pgTAP green in this repo has been against a partially-migrated database

https://github.com/GaryOcean428/crm7/issues/1506

Snapshot updatedAt: 2026-08-24T03:27:03Z. Open at capture; re-read live.

## 17 migrations have been failing in CI, silently, since May

Exposed the moment `pgtap.yml` stopped swallowing failures (PR #1503). They are now **quarantined and visible** in `supabase/migrations/KNOWN-BROKEN-IN-CI.txt`. This issue is the programme to empty that file.

## What was happening

```bash
ERR=$(psql ... | grep ERROR | head -1) || true
if [ -n "$ERR" ]; then echo "::warning::... failed; continuing"; fi
# ...then a second loop recorded EVERY post-baseline version as applied, regardless.
```

Worse than "downgraded to a warning": `$?` came from **grep**, so a psql failure whose message lacked the literal string `ERROR` was never detected at all.

## Why it matters more than 17 broken files

**Every pgTAP run in this repo has executed against a partially-migrated database and reported green.**

Any assertion about an object one of these migrations should have created was **vacuous** — the suite passed *because* the thing under test was absent, which reads identically in the log to it existing and behaving correctly.

That includes the **cross-tenant isolation suites**. Their e2e fixture tenant pair (`20260807100000`) was itself one of the casualties — a migration written *because a real client had been used as the victim in a security test*. So the tests meant to prove isolation fixture-against-fixture have been running with no fixtures. Fixed in #1503; the rest remain.

This is the estate's already-documented **"live but unrebuildable schema"** condition. What is new is that it is now measurable.

## The quarantine is a ratchet, not an exemption list

```
a migration NOT listed that FAILS    -> job FAILS   (the protection)
a migration listed that SUCCEEDS     -> job FAILS   (the ratchet)
```

The second rule is what prevents rot: the moment a quarantined migration starts applying, CI demands its line be removed. The list can only shrink, and its length prints every run:

```
::notice::migration replay debt: N quarantined (crm7#1504) — this number must only go down
```

## Order of work

1. **`20260807079000`** — the real SQL defect. Small, and it is not environment-dependent.
2. **The four seed migrations** — make them idempotent/conditional, the way `20260807100000`'s real-client guard was scoped in #1503 (skip when the referenced rows are absent rather than aborting).
3. **The Vault and storage-bucket dependants** — either provision them in CI or guard on their presence.
4. **The baseline-shape mismatches** — these are the real "unrebuildable schema" core and may need a baseline regeneration. Note the standing warning: regenerating a baseline marks all migrations applied, so **nothing replays and every seeded row vanishes**.

## Acceptance

- `KNOWN-BROKEN-IN-CI.txt` contains zero entries.
- A deliberately-broken migration added in a test PR turns the job red **from the migration step** — proven, not assumed.
- The cross-tenant isolation suites are re-run and confirmed to be finding both fixture tenants, with a passing positive control.

**Until that last point is done, treat every historical pgTAP green in this repo as unverified.**
