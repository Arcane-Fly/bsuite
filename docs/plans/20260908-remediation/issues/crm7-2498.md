# Host supervisors can reach GTO-internal pages: the route gate checks a permission, not whose host it is

https://github.com/GaryOcean428/crm7/issues/2498

Snapshot updatedAt: 2026-09-06T10:41:27Z. Open at capture; re-read live.

Found during the crm7#1675 sibling audit. Filed separately because #1675's fix (PR #2496) closes the **data** boundary and this is the **route** boundary — they need different remedies and should not be conflated.

## What

`src/components/auth/protected-route.tsx` gates on a generic `Permission` string. `src/hooks/usePermissions.ts` gives the `host_employer` role — which `user_tenants.portal_role = 'host_contact'` normalises to (`usePermissions.ts:686`) — these permissions:

```
usePermissions.ts:65   host_employer: [
              :84       'view_contracts',
              :87       'view_charge_rates',
              :88       'view_billing',
              :92       'view_contacts',
              :98       'view_hosts',
```

`/contracts` is gated on `permission="view_contracts"` alone (`App.tsx:2764-2767`) and `/hosts/:id` on `permission="view_hosts"` (`App.tsx:2973`). Neither checks that the page's *subject* belongs to the caller's own host. `src/pages/hosts/[id].tsx:101` takes `params.id` straight from the URL.

So a host supervisor can navigate to internal, GTO-staff-shaped pages, and on `/hosts/:id` can substitute **another host's** `employers.id`.

## Severity, honestly

**Materially reduced by #2496, not eliminated.** Once that migration applies, `employers`, `clients`, `sites`, `training_contracts`, `invoices`, `invoice_line_items`, `payments`, `host_agreements` and `site_visits` are all scoped to the supervisor's own host in RLS, so these pages render empty or own-host-only rather than leaking. Before it, `/contracts` listed every host agreement and training contract in the tenant.

What remains after #2496 is a **defence-in-depth and UX defect**, not a live data leak:

1. A host supervisor sees GTO-internal navigation and pages that are not theirs, mostly empty. That is confusing and it advertises surface area.
2. The gate is one predicate away from being a leak again — any future table that gets a route before it gets a host limb is exposed by construction. The route layer should not be relying on RLS to be the only thing that knows about hosts.
3. `view_billing` / `view_charge_rates` on the `host_employer` role deserve their own review; the comment at `usePermissions.ts:1` says this role "sees only their workers/placements/timesheets", which is narrower than what the list actually grants.

## Suggested shape

Either (a) give `ProtectedRoute` an ownership predicate for host-scoped routes, not just a permission string, or (b) route host supervisors to `/portal/host-employer` and keep them out of the internal `/contracts` and `/hosts/:id` shells entirely. (b) is likely less code and matches the intent recorded in the role's own comment.

## Not doing this in #2496

#2496 is the RLS fix and is already broad (9 tables). Mixing a route-gate change into it would make a security migration harder to review and harder to revert.
