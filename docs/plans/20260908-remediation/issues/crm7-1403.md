# [P1] requoteOnRiseService throws on FutureBuild's 8 snapshots and aborts the whole batch — 8/8 of the real client's calc_inputs are incomplete

https://github.com/GaryOcean428/crm7/issues/1403

Snapshot updatedAt: 2026-08-24T03:28:18Z. Open at capture; re-read live.

Surfaced during the review of #1399 (which is merged and is **not** the cause). Pre-existing, live, and it hits the only real client.

## Measured, grouped by tenant

```
tenant              | snapshots | incomplete calc_inputs
--------------------+-----------+-----------------------
Braden Group        |     1     |  1
bsuite Platform     |     4     |  0
FutureBuild Academy |     8     |  8      <-- the real client
```

Nine of thirteen `charge_rate_snapshots` rows carry only **2 keys** in `calc_inputs` — no `wage`, no `allowances`, no `funding`. **All eight FutureBuild rows are among them.**

Reporting this grouped rather than as "9 of 13" deliberately: an aggregate would have read as a demo-data problem. It is the opposite — the demo tenant is the clean one.

## Why it breaks

`src/services/requoteOnRiseService.ts:366-368`:

```ts
const priorConfig = priorSnapshot.calc_inputs as unknown as CalcConfig
sharedCalculate({ ...priorConfig, wage: newBaseRate })
```

`calculate()` requires ~27 fields. On a 2-key object it throws — verified by execution during the #1399 review:

```
calculate({ wage: 25.5, overheadType: 'percent', … })
  → Cannot read properties of undefined (reading 'filter')   // allowances
```

That call sits inside `for (const placement of affected)` **with no try/catch**. So the first FutureBuild placement `generateRequoteDraftsForRateChange()` reaches throws, and **the entire batch aborts** — every later placement, including any healthy one, is silently skipped.

## Severity

P1, not P0: requote-on-rise fires on an award-rate change, nothing has ever billed, and the failure is a throw rather than a wrong number. But it means the award-rise watchdog is **non-functional for the only tenant that matters**, and the failure mode is an aborted batch rather than a reported one — nobody learns that the other placements were skipped.

## Two fixes, and the second is the real one

1. **Guard the loop.** Wrap the per-placement `sharedCalculate` so one bad snapshot skips that placement and is *reported*, rather than aborting the batch. This is the immediate containment.

2. **Decide what an incomplete snapshot means.** A 2-key `calc_inputs` cannot be requoted from — it is missing the inputs by definition. Options: backfill from the quote's other columns where possible; mark such snapshots explicitly non-requotable so they are excluded with a reason instead of exploding; or treat the write path that produced them as the defect and fix that. Do not silently skip them — that is how the batch quietly stops covering rows nobody notices.

Worth checking which writer produced the 2-key rows, since #1399 has now made the R8 push path validate the full `CalcConfig` shape before writing. That closes one future source; it does nothing for the nine already there.

## Do not touch FutureBuild's data to investigate

Read-only queries only. All the measurement above was `SELECT`.

## Related
