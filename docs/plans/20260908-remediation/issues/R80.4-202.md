# FAIRWORK_API_KEY_SECONDARY is not configured, and the configured FWC_API_KEY returns 401 on every probe

https://github.com/GaryOcean428/R80.4/issues/202

Snapshot updatedAt: 2026-08-24T10:59:42Z. Open at capture; re-read live.

Found while auditing which GitHub Actions secrets R80.4 actually needs. **This is a configuration action, not code** — the code side is #201.

## The measurement

This repo tries three key names. From its own probe — five requests each, three seconds apart, against `/awards/MA000020/pay-rates`:

```
FAIRWORK_API_KEY             200 200 200 200 200
FAIRWORK_API_KEY_SECONDARY   200 200 200 200 200
FWC_API_KEY                  401 401 401 401 401
```

What is actually configured in R80.4's Actions secrets:

| name | configured | authenticates |
|---|---|---|
| `FAIRWORK_API_KEY` | ✅ (added 2026-08-24 03:07) | ✅ |
| `FWC_API_KEY` | ✅ | ❌ **401 × 5** |
| `FAIRWORK_API_KEY_SECONDARY` | ❌ **absent** | ✅ |

**The two configured names include the dead one. The working fallback is the one missing.**

## Why it matters

Azure API Management issues a primary *and* a secondary subscription key precisely so one can be rotated without downtime. That is why `lib/fwc-api-key.mjs` tries all three in order.

Right now there is effectively **no fallback**. The moment `FAIRWORK_API_KEY` is rotated, the only remaining candidate is `FWC_API_KEY`, which 401s — nothing resolves, and until #201 lands, benchmarks **D13 and D15 waive themselves green** having exercised nothing.

## Two actions

1. **Add `FAIRWORK_API_KEY_SECONDARY`** to R80.4 → Settings → Secrets and variables → Actions → repository secrets. (Repo scope specifically: no job here declares `environment:`, so environment-scoped secrets are unreachable, and `GaryOcean428` is a User account so there is no org scope.)
2. **Remove or replace `FWC_API_KEY`.** A configured secret that has never authenticated reads as a working fallback to anyone looking at the list, and is the reason "there are two keys configured" is misleading. I have not touched it — deleting a secret is not mine to do.

## Scope note, since it came up in the same audit

R80.4's three workflows reference **no Supabase secrets at all** (0 mentions of "supabase" in any of them). Nothing Supabase needs adding here; the parent repo holds those and is what sweeps this one.
