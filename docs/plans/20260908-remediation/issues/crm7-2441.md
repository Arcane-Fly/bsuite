# ActingAsBanner cannot see a scope change made in another tab, while its docblock says it always can

https://github.com/GaryOcean428/crm7/issues/2441

Snapshot updatedAt: 2026-09-05T12:19:21Z. Open at capture; re-read live.

Found by a read-only authz review (`bsuite-rls-authz-red-team` + `auth-supabase`) over the tenant-scoping diffs; report at `~/.claude/projects/-home-braden-Desktop-Dev-bsuite/evidence/2026-09-05/authz-review-tenant-scoping-2431-2432-2436.md`, finding F2. Not an authorisation bypass — the server re-evaluates `acting_scope_tenant_id()` on every request regardless — but the banner's own docblock claims something it does not do.

`ActingAsBanner`'s `['acting-as-scope']` query has no `refetchInterval`, the QueryClient default is `refetchOnWindowFocus: false`, and the component mounts once per tab inside the persistent `MainLayout`. The 30-second tick only recomputes the expiry label from the row already held. So a scope change made in another tab, or on another device, is not noticed until an unrelated reload — while the docblock says such changes are always noticed.

This is the FOLLOW-83 mismatch class recurring on a narrower path: what the page shows and what the server applies drift apart, and the component that exists to close that gap is the one carrying the stale claim.

Two shapes, either acceptable: a short `refetchInterval` on that query, or a cross-tab nudge over `storage` / `BroadcastChannel` — the app already does the latter for `logoutSync`, so the pattern exists. Whichever is chosen, the docblock's claim should be made true or narrowed to what the code does.
