# §5.3 violation: resting dark cards carry a 0.1316 Electric Cyan elevation shadow, and page-builder ships the same to every consumer

https://github.com/GaryOcean428/crm7/issues/2506

Snapshot updatedAt: 2026-09-06T14:51:21Z. Open at capture; re-read live.

`docs/20260822-border-elevation-token-system-spec-v1.00F.md` **§5.3**, a line carrying the
spec's own `← the change` marker:

> **Accent MUST NOT be used for:**
> - any resting container edge — border or ring ← the change
> - **dark-mode elevation shadows** ← the change

crm7 does. Measured on production `crm.crm7.app` @ `ce4ff81`, dark **emulated and reloaded**
(never a forced `.dark` class), transitions killed before the read, with the instrument's own
controls bitting in the same call (a known accent must round-trip C 0.132 / H 191.7, a grey
must read C 0, a `lab()` string must parse, a junk string must return UNPARSEABLE not 0):

| surface | n | resting `box-shadow` accent layers | max chroma @ hue |
|---|---:|---|---|
| shadcn `Card` — `… shadow-light-md dark:shadow-card-glow …` | 4 | `/0.278 0 0 0 1px`, `/0.22`, `/0.078` | **0.1316 @ 191.9** |
| page-builder grid chrome — `… bg-card border-[…] shadow-sm dark:shadow-[var(--glow-card,none)]` | 7 | `/0.302 0 0 0 1px`, `/0.349 0 0 14px -4px` | **0.1324 @ 191.2** |

Hue 191–192 is Electric Cyan. The estate's ambient ramp ink is chroma **0.02**; these are
~6.6× that, at rest, in dark mode.

## Two call sites, and the second is the one that matters

1. **crm7-local.** `crm7/src/index.css:353` registers `--shadow-card-glow: var(--glow-card, none)`
   in `@theme inline`, consumed as `dark:shadow-card-glow` by the shadcn `Card`
   (`card.tsx:45`). `--glow-card` resolves from `@bsuite/theme@1.5.1` `vars.css:779-784` to
   `0 0 0 1px color-mix(… 30%) , 0 0 14px -4px color-mix(… 35%)`.
2. **`@bsuite/page-builder`.** `PageGridLayout.tsx:505` has
   `dark:shadow-[var(--glow-card,none)]` baked into the grid-item chrome string. That is a
   **shared package shipping a §5.3 violation to every consumer that renders the chrome** —
   measured live on crm7's canvas as 7 elements at 0.1324. BSU's canvas does not render that
   element with chrome, so it does not manifest there today; that is configuration, not
   compliance, and it will manifest the moment a consumer turns the chrome on.

## Why this went unnoticed for a week

The spec's own **"Implementation record — closed 2026-08-29"** (lines 13–38) records as a
**verified closed defect**:

> "resting `var(--glow-card)` sites: crm7 **0** · BSU 0 · conduit 0 · throughput 0"
> … "no resting inset-shadow rule survives"

Live rendering contradicts it for crm7. Worse, **`visual-probe.js` V-C7 required this
violation** — its threshold was anchored to `--card-glow-source`, the token §5.4 retired — so
the gate was passing crm7 and failing every compliant app. Three issues were filed against the
compliant apps (throughput#481, conduit#694, business-suite-unified#1179) and none here.

Gate fixed in **Arcane-Fly/.github-private#20**; on the same page load crm7 goes from
`INCOMPLETE with 0 elevation FAILs` to **`BLOCK with 11`**.

## Not braden

braden's resting shadow is 0.0941 at hue **90.4** — Braden Gold, not Electric Cyan. §0 of the
spec puts Corporate explicitly out of scope, and the implementation record says so in terms
("braden is untouched and keeps its 32 resting rings **by design**"). It is exempt, and the
rewritten probe reports that exemption as INFO rather than skipping it silently.

## What the fix is, per §5.4/§5.5 — not a deletion

The glow is **relocated, not removed**: it becomes the hover/focus affordance. So both call
sites want the accent moved behind `:hover` / `:focus-visible`, with the resting state on the
achromatic ramp — the shape conduit, throughput and BSU already have. Two things to check
before doing it, both already paid for elsewhere in this estate:

- `--tw-ring-shadow` is **not** the slot to move it to; a focus ring lives there and would be
  silently replaced in dark mode (WCAG 2.4.7).
- The page-builder change is a package release and reaches five consumers at once, so it wants
  its own before/after render per consumer, not a source diff.

Found by the SHIP lane on bsuite#3119 after the gate itself was re-derived from the spec.
