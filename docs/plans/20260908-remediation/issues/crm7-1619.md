# [P2] Compliance registers: row-level write controls still gated on view_compliance (the half #1597 did not cover)

https://github.com/GaryOcean428/crm7/issues/1619

Snapshot updatedAt: 2026-08-24T03:28:25Z. Open at capture; re-read live.

**Found by:** crm7#1597 lane, 2026-08-11. Same class as #1597, which fixed only the CREATE affordance.

## Problem

#1597 added `manage_whs_audits` / `manage_lln_assessments` and gated the **create** controls on the compliance registers. The **row-level write** controls were left on the page-level `view_compliance` gate:

- `src/pages/compliance/whs-audits/index.tsx` — the "Advance status" button on each row performs an `UPDATE` on `whs_audits` and is not permission-gated.

RLS `is_gto_staff(tenant_id)` admits `gto_admin` / `gto_staff` / `field_officer` for that UPDATE, so for those roles the write succeeds. For a `view_compliance`-only role that RLS refuses (`training_provider`, `executive`), the button renders and the write fails — the same UI-honesty problem #1597 fixed one control to the left.

## Scope this properly before fixing

Do not patch just this button. Sweep the compliance registers for **every** control that mutates:
- status transitions, inline edits, delete/archive, bulk actions
- the LLN register's equivalents

For each: does the role that can see it hold a permission RLS will honour? Gate on the entity permission (`manage_whs_audits` / `manage_lln_assessments`) introduced by #1597, not on `manage_compliance` — that one excludes `field_officer`, whose job these records are. See #1597 for the full matrix and why.

## The broader question worth answering once

The app permission model and RLS are two independent authorisation systems that have already drifted twice in this cluster. `is_gto_staff()` is a role-set predicate; `usePermissions.ts` is a capability table. Nothing asserts they agree.

A contract test could: for each `manage_*` permission, assert the set of app roles holding it matches the set of `gto_role` values the corresponding RLS predicate admits. That would have caught both #1597 and this issue before either shipped.

- **Validation loop**: §9.1 output-equivalence
- **Equivalence target**: for each mutating control, a role WITH the permission completes the write and a role WITHOUT it neither sees the control nor can complete the write — proven at the DB layer by executing as that role, not by reading policy text
