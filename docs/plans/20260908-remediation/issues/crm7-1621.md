# [P3] React.forwardRef may blind react-hooks rules — and crm7#1582's root cause was probably misattributed

https://github.com/GaryOcean428/crm7/issues/1621

Snapshot updatedAt: 2026-08-11T06:58:37Z. Open at capture; re-read live.

**Found by:** the crm7#1598 lane, 2026-08-11, while building the positive control it was asked for. Not the question it was sent to answer.

**Versions:** `eslint-plugin-react-hooks` 7.1.1, `react` 19.2.8, `eslint` 10.8.0.

## First, the question #1598 asked — answered NO

The React Compiler namespace bug (facebook/react#35280) **does not** reach `react-hooks/refs`, `/purity` or `/immutability` on 7.1.1. Each rule was positive-controlled in bare call form, confirmed enabled for the test path via `--print-config`, then converted character-for-character to `React.useRef` / `React.useMemo` / `React.useState` and re-run. **All three fired identically in both forms.** Exposure: 0.

## But the original attribution in #1582 looks wrong

A *minimal* namespace-form fixture would not reproduce the silence #1582 was built on. So the lane extracted the actual pre-fix `localised-date-input.tsx` (`git show 1de03057^:...`) and ran it verbatim — silent, rule confirmed enabled. Then bisected:

- converting **only** its `React.useEffect` → bare `useEffect`, everything else untouched → **still silent**
- isolating just the `React.forwardRef(function Name(props, ref) {...})` wrapper around a known-working minimal fixture → **reproduced the silence**, for `set-state-in-effect`, `refs` *and* `immutability`, **in both call forms**

So the mechanism behind the one file #1582 used as its evidence was very likely **`React.forwardRef`**, not the receiver-vs-property callee bug it was attributed to. #1582's *fix* stands — the effect was a genuine derived-state violation and refactoring it was right. Its **diagnosis** is the part in doubt.

## Not clean, and deliberately not overclaimed

The lane could not reproduce it for `purity`: a synthetic forwardRef + purity fixture went silent, but the real `sidebar.tsx` — a forwardRef component with a genuine `Math.random()` in `React.useMemo` — fires correctly, before and after that file's edit. So the boundary is uncharacterised.

**Exposure today is nil.** Of the 22 files across `REFS_FILES` / `PURITY_FILES` / `IMMUTABILITY_FILES`, only `sidebar.tsx` uses `forwardRef` at all, and it is the one confirmed still firing. No phantom suppression entries exist because of this.

## Why it still matters

If `forwardRef` can blind these rules, the suppression register undercounts for a **third** independent reason, on top of the two already recorded:
1. synchronous-only detection (setState after `await`/`.then()` is invisible)
2. ~~the namespace bug~~ — ruled out above
3. this

`forwardRef` is pervasive in shadcn primitives. A component authored inside one could carry a real violation that no lint run will ever show.

## What would settle it
- A minimal reproduction that fires without the wrapper and goes silent with it, held constant otherwise, for each affected rule — then upstream it.
- Or: force each rule over every `forwardRef` component in `src/` and compare against the same components mechanically unwrapped.
- Either way, **positive-control first.** A rule that flags nothing in both forms proves nothing, which is the trap that produced the wrong attribution in the first place.
