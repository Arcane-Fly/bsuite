# [P2] 3 error boundaries for 443 pages — one lazy-route error blanks a whole section

https://github.com/GaryOcean428/crm7/issues/1629

Snapshot updatedAt: 2026-08-11T07:16:43Z. Open at capture; re-read live.

**Source:** operator full-spectrum review, 2026-08-11. Re-verified: **3** `<ErrorBoundary>` usages in `src/App.tsx`.

## Finding

Three boundaries for **443 pages**. One render error in a lazy route can blank an entire section rather than the page that failed.

## Why it is cheap here

`src/App.tsx` already wraps every lazy route in `retryImport` and a `<S>` Suspense helper. A per-route boundary drops into that same wrapper — the seam exists, and Sentry is already wired to receive.

## The dependency worth respecting

`src/App.tsx` is **4,019 lines** (re-verified — it has grown; the review measured 3,859). Threading a boundary through 362 route declarations by hand means touching that file 362 times.

**Extracting per-domain route manifests first makes this mechanical** rather than a 362-line diff. The two should be sequenced: extraction, then boundaries. See the App.tsx decomposition issue.

## Related, same class

~23 silent `.catch(() => {})` handlers (the review's count; my narrower grep found 2 — **trust the review, my pattern was blunt**). Each is a debugging dead end: an error that reaches one of these leaves no trace anywhere, which is how a defect survives a log review. Worth a sweep in the same pass — every one either handles the error, reports it, or explains in a comment why discarding is correct.

## What a good boundary does here

Not just "something went wrong". It should name the route, offer a recovery action (retry / back to dashboard, as the inline 404 already does), and report to Sentry with the route in the tags — otherwise a section-level failure is indistinguishable from a blank page in the logs.
