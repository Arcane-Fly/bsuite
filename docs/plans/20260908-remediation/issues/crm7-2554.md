# tenants.usi_org_code does not exist though its migration is recorded as applied — the govt-integrations save cannot succeed, and the ledger is now untrustworthy in both directions

https://github.com/GaryOcean428/crm7/issues/2554

Snapshot updatedAt: 2026-09-07T14:43:25Z. Open at capture; re-read live.

## A migration recorded as applied whose column does not exist

`tenants.usi_org_code` does not exist on production. Nor does `tenants.ram_environment`.
Measured read-only against `information_schema` on 2026-09-07 — the full `tenants` column list
contains neither.

The migration that adds it is recorded as **applied**:

```
crm7/supabase/migrations/archive/20260304000061_usi_org_code.sql
  ALTER TABLE tenants
    ADD COLUMN IF NOT EXISTS usi_org_code TEXT
      CHECK (usi_org_code IS NULL OR (LENGTH(...) BETWEEN 1 AND 8 AND ... ~ '^[A-Za-z0-9]+$'));

supabase_migrations.schema_migrations  version = 20260304000061  →  PRESENT
```

**No `DROP COLUMN` for it exists in any of the six app trees** (`grep -rn "DROP COLUMN"` across
all `*/supabase/migrations`, filtered for usi/ram — nothing). It is not a version collision
either: only crm7 has a file at `20260304000061`.

So the ledger says applied, the statement is `ADD COLUMN IF NOT EXISTS`, and the column is not
there. **I have not identified the mechanism and am not going to guess at one.** The candidates
I can see but cannot distinguish without more evidence: a ledger row inserted by a repair without
the file running, or the file running against a different database.

## Why it matters beyond one column

This is the **inverse** of bsuite#3171. There, 70 BSU migration files are absent from the ledger
while their objects exist. Here, a ledger row exists while its object does not. Taken together
the ledger cannot currently be trusted in either direction, which is the one question it exists
to answer: *is this deployed?*

## What it breaks today

The whole government-integration configuration surface cannot read or write its own settings:

- `src/pages/settings/govt-integrations.tsx` UPDATEs `tenants.usi_org_code` → 42703.
- `src/lib/integrations/usi/usiService.ts` selects `usi_org_code, ram_environment` from
  `tenants` → 42703.

crm7#2553 repoints that page's tenant lookup (it previously read a non-existent
`user_profiles.tenant_id` and told the user **"Tenant not found"**, blaming their account for a
broken query). That fix is real but it is not sufficient — the save still cannot succeed, and
#2553 says so in the code and in its own commit message rather than implying the page works.

## What would settle it

1. Decide whether these columns belong on `tenants` at all. The page's own comment already flags
   the concern — *"config columns on the identity table are a latent multi-writer hazard — they
   belong in a crm7-owned settings table"* — and `tenants.settings` (jsonb) exists.
2. Whatever the target, it needs a migration that actually runs, plus a check that the ledger row
   and the object agree afterwards.
3. Separately worth having: a gate that samples ledger rows and asserts the object they claim to
   create exists. Both #3171 and this issue would have been caught by it, from opposite
   directions.
