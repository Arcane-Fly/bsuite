# USI verification selects people.usi_verified_at and people.usi_verification_source — one is on apprentices, the other exists nowhere, and every apprentice silently reads as unverified

https://github.com/GaryOcean428/crm7/issues/2555

Snapshot updatedAt: 2026-09-07T14:22:46Z. Open at capture; re-read live.

## USI verification reads two columns the schema does not provide, and reports every apprentice as unverified

Measured read-only against production on 2026-09-07.

```
tables with usi_verified_at          →  apprentices           (NOT people)
tables with usi_verification_source  →  none
people                               →  has `usi`, has `employment_type`; neither of the above
```

`usi_verification_source` exists in **zero** places: no table, **no migration file in any of the
six trees** (`grep -rln usi_verification_source */supabase/migrations` → nothing), and **not in
`src/types/supabase.ts`** (0 occurrences). It was never designed, not lost.

Two call sites select both from `people`:

- `src/lib/data/usiQueries.ts:26-32` — `.from('people').select('… usi, usi_verified_at, usi_verification_source, status')`
- `src/lib/integrations/usi/usiService.ts:399-404` — `getVerificationStatus(personId)`

### The failure is invisible, and it defaults to "unverified"

`getVerificationStatus` logs and returns a degraded default:

```ts
if (error) {
  logger.error('[USI] Failed to fetch verification status:', error)
  return { usi: null, source: 'format_only', verifiedAt: null, error: '…' }
}
```

PostgREST rejects the select with 42703, so **every** call takes that branch. Every apprentice
reads as `format_only` / never verified, regardless of what was actually recorded — and
`apprentices.usi_verified_at`, which is the column that really exists, is never consulted.

That is worse than an empty list: a compliance-relevant status that is **always the pessimistic
value** and always looks like a legitimate answer.

### What it needs, and why I have not just renamed it

Not a rename. Two separate questions:

1. **Which table owns USI verification state?** `apprentices.usi_verified_at` exists and holds
   the real column; `people` is what both call sites query, and `usiQueries` filters
   `.in('employment_type', ['apprentice','trainee'])` — i.e. it is reaching for apprentice-shaped
   people. Pointing the reads at `apprentices` is the obvious move, but it changes the join and
   the 58-vs-20 row counts say the two are not interchangeable.
2. **Does `usi_verification_source` exist as a concept at all?** Nothing in the schema or the
   migrations has ever provided it. Either it needs designing and migrating, or the code should
   stop asking for it and derive the source another way.

Both are decisions about the data model, so they are routed rather than taken.
