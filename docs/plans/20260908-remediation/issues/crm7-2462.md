# createEntityStore casts away the schema, so a page can write columns that do not exist

https://github.com/GaryOcean428/crm7/issues/2462

Snapshot updatedAt: 2026-09-05T15:08:26Z. Open at capture; re-read live.

Surfaced by gating #2455, where a page was written against columns that do not exist and every check in the repo passed. This issue is about why nothing caught it, because that part is estate-wide.

## The hole

`createEntityStore` takes `tableName` as a `string` and casts the result `as unknown as T`. The table name is never connected to the generated database types, so the row shape a caller declares is accepted on the caller's word alone.

The repo already knows the truth. `src/types/supabase.ts:2037` says `case_notes` has `content: string`, `subject: string`, and no `visit_type`. That file is generated from the live schema and is correct. It simply is never consulted, because the cast discards the question before it is asked.

So `tsc` exits 0 while a page writes `visit_type`, `visit_date` and `field_officer_id` to a table with none of them, and reads `content` as JSON from a `text NOT NULL` column.

## Confirmed against production

```
note_type   text  NOT NULL      subject  text NOT NULL
content     text  NOT NULL      person_id / employer_id / training_contract_id  uuid
rows: 0
```

No `visit_type`, no `visit_date`, no `field_officer_id`. `subject` is NOT NULL with no default and is collected by no page. The table has never received a row, so nothing has ever exercised the write path to find out.

## Why this is worse than one broken page

A store helper that erases the schema turns a compile-time error into a runtime failure at the moment a user presses Save. Every consumer of `createEntityStore` has the same exemption, and the failure only appears when someone finally writes a row — which, on a table with zero rows, may be a customer.

Tests do not close it either: mocking the store wholesale, which is the normal thing to do, removes the last place the mismatch could show up.

## Fix direction

Make the table name a key of the generated `Database['public']['Tables']`, and derive the row, insert and update types from it rather than accepting a caller-supplied `T`. The cast then has nothing to hide and the existing generated types start doing the work they were generated for.

That will surface existing mismatches across every consumer. That is the point, and the count of what it surfaces is the real acceptance measure for this issue.

## Acceptance

A store declared against a non-existent column fails `tsc`. A store declared against a real table with a wrong field type fails `tsc`. Then run it across the estate and report what it found, per table, rather than fixing silently.

A test asserting only that a correctly-typed store still compiles passes today and proves nothing.
