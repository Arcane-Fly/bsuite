# A permission error is reported to users as "this table is being provisioned"

https://github.com/GaryOcean428/crm7/issues/2465

Snapshot updatedAt: 2026-09-05T15:27:48Z. Open at capture; re-read live.

Seven features tell the user they are not available yet. All seven tables exist on production. I confirmed each one under a read-only transaction:

```
signature_requests             -> signature_requests
whs_incidents                  -> whs_incidents
whs_risk_assessments           -> whs_risk_assessments
whs_policies                   -> whs_policies
people_training_day_overrides  -> people_training_day_overrides
dashboards                     -> dashboards
host_capacity_assessments      -> host_capacity_assessments
```

Every one resolves. Not one is absent.

## What the user is told

> "The safety policies database table is being provisioned. This feature will be available shortly. Contact your administrator if this persists."

The same sentence, with the noun swapped, appears on incidents, risk assessments and signature requests. Six of the seven sit on routes reachable from the navigation.

So someone opens WHS incidents, is told the system is still being set up, and contacts their administrator. The administrator finds a table that has been there all along. The message is not merely stale, it actively sends the user somewhere with a question that has no answer.

## Why this class is worth its own issue

These were written as graceful degradation, which was the right instinct when the tables genuinely did not exist. The problem is that nothing expires them. A guard that says "not yet" has no mechanism to notice that "yet" arrived, so it keeps saying it indefinitely — and it is precisely the kind of message that stops anyone investigating, because it reads as a known state rather than a fault.

That is the same shape as the case-notes banner in #2464, which said the backend was not connected while the table existed and had never matched the code. A notice explaining an absence is the most effective way to stop anyone measuring whether the absence is real.

There is an eighth instance that is worse because it cannot self-correct at all: a hardcoded refusal in the field-officer assistant tools, which will keep declining regardless of what exists.

## What "fixed" means here

Not deleting the guards. They should fire on a real failure — a table genuinely missing, or a permission denial — and say which. What is wrong is that the message asserts a cause it has not checked.

For each of the seven: confirm the feature works against the live table, remove the provisioning notice, and let a genuine error surface as an error. Where a feature turns out to be incomplete behind the guard, that is a separate finding and should be filed as one rather than left under a message that misdescribes it.

## Acceptance

Each of the seven either works, or fails with a message that names what actually went wrong. No message claims a table is being provisioned. And a check that fails when a "being provisioned" string ships alongside a table that resolves, so this cannot silently return.

## Method

Grep for the provisioning and not-connected phrasings across the app, then resolve every named table against production with `to_regclass`. Seven found, seven present. I have not audited what each feature does once its guard is removed, and that is the next question rather than something this issue answers.
