# [P1] The RLS invariant suite is advisory on the branch where RLS changes land

https://github.com/GaryOcean428/crm7/issues/2499

Snapshot updatedAt: 2026-09-06T10:00:32Z. Open at capture; re-read live.

## What

`Anon-context RLS tests (Constraint C10)` — the pgTAP database suite that carries this
estate's RLS invariants — **is not a required check on `development`**, which is the branch
every RLS migration lands on.

## Measured, end to end

Verified today against `GaryOcean428/crm7`:

1. **The check runs, and it catches real defects.** On crm7#2496 it is currently `fail`
   (3m0s), correctly flagging `50_t1b_developer_reads_all.sql` A4: two new
   `AS RESTRICTIVE FOR SELECT` policies that never name `is_platform_developer()`. A
   restrictive policy ANDs, so it can strip a permissive developer read-all grant.

2. **It is not in the required list.** Classic branch protection on `development` requires
   15 checks:

   ```
   gitleaks · build-and-test · Coverage floor · postgrest-column-lint ·
   entity-store-tenant-scope · DOM Layout Invariants ·
   Verify BS OAuth session sync wired · Dependency audit (fails on critical) ·
   SECURITY DEFINER public function guardrails · dry-lint · rls-jwt-lint · e2e ·
   lighthouse · report_catalog_* drift vs live schema · BSuite 9-signal drift scan
   ```

   `Anon-context RLS tests (Constraint C10)` is absent.

3. **The rulesets do not supply it either.** Two active rulesets:
   `default` targets `~DEFAULT_BRANCH` and requires only `build-and-test` +
   `DOM Layout Invariants`; `development` targets `refs/heads/development` and requires
   **zero** checks.

4. **`rls-jwt-lint` is required and does not cover this.** It passes on #2496 while C10
   fails. It is a lint over source; C10 runs the policies against a database.

## The consequence

Once the slower required checks finish, **GitHub would permit a merge to `development` with
the RLS invariant red.** The estate's RLS test suite is advisory on the one branch where RLS
changes are made.

This is not hypothetical: it is the current state of crm7#2496, a PR that rewrites RLS on
nine tables of a shared production database. The only thing stopping that merge is a human
reading the check list.

## Why it matters more than a normal missing gate

A gate that runs, goes red, and is ignored by the merge button is **worse than no gate**,
because its presence in the check list reads as coverage. Anyone scanning a PR sees an RLS
suite and concludes RLS is gated.

## Fix

Add `Anon-context RLS tests (Constraint C10)` to the required checks on `development` — and
audit the same question for every app repo sharing this Supabase project, since the database
is shared and a policy merged in one repo affects all of them.

While there: reconcile classic branch protection with the `development` ruleset. Having a
ruleset that targets the branch and requires nothing is an invitation to assume it is doing
work it is not.

## Acceptance

- C10 is required on `development` in every repo whose migrations reach the shared project.
- A PR with C10 red cannot be merged by the button.
- The check is verified to actually block, by observing a red C10 refuse a merge — a required
  check that was added but never proven to block is the same defect one level up.
