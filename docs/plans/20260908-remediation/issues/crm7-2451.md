# A custom page save reports success when only the revision was written

https://github.com/GaryOcean428/crm7/issues/2451

Snapshot updatedAt: 2026-09-05T13:43:04Z. Open at capture; re-read live.

Reported by the copilot-customization-audit lane, which modelled the service in a VM against a mocked response contract. I verified it against the source and the live schema, and there are two consequences their report does not name.

## The defect

In [customPageService.ts:139](crm7/src/services/customPageService.ts#L139), `savePageRevision` writes the revision row and checks it, then writes the page itself and checks nothing:

The revision insert destructures its error and throws on it. The `custom_pages` update discards both the error and the affected-row count, and the function returns the revision as though both writes landed. A row-level security refusal, or an update that matches no row, is indistinguishable from success.

## Consequence one: the user watches their work disappear while being told it saved

The caller re-reads the page after saving, which was written as a safety measure and is commented as one. When the page update silently failed, that re-read returns the *old* layout, and the handler assigns it straight into the editor. The user's arrangement is replaced on screen by the version they were trying to overwrite, and the success toast fires in the same breath, quoting a version number that never incremented.

So the safety measure is what destroys the visible work. Without the re-read the user would keep their layout in the canvas and merely fail to persist it.

## Consequence two: the revision history silently corrupts

`custom_page_revisions` in the production baseline has a primary key on `id` and a foreign key on `page_id`. **There is no unique constraint on `(page_id, version)`.**

The version is computed as the page's current version plus one. When the page update fails, the page's version does not move, so the next save computes the same number again and inserts a second revision at that version. Nothing refuses it. `getPageRevisions` orders by version descending, so the duplicates tie and their relative order is arbitrary. A user reading the history sees two rows both labelled the same version, with no way to tell which is which.

The restore path calls the same function, so restoring a revision carries the identical failure.

## What this is not

This is executable service behaviour, not proof that live row-level security currently refuses this update. Nobody has shown a real tenant hitting it. The defect is that the code cannot tell the difference, so if it ever happens the user is told the opposite of the truth.

## Acceptance

- A rejected update and a zero-row update must both fail loudly. Neither may return a revision or fire a success toast.
- The page row and the revision must agree after a save, or the save must not report success.
- Two saves racing must not produce two revisions at one version. Decide whether the fix is a unique constraint on `(page_id, version)`, an atomic function that writes both, or a version taken from the database rather than computed in the client, and say why.
- On the deploy: edit, save, reload, and confirm what is on screen is what is stored. Then the restore path the same way.

Tests must fail against the current service. A test that only exercises the success path passes today.
